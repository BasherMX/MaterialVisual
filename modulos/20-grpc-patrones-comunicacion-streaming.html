gRPC & Patrones de Streaming

Protocolo de comunicación de alto rendimiento basado en HTTP/2 y serialización binaria con Protocol Buffers (Protobuf). Explora los 4 patrones de llamada canónicos y la reducción drástica de latencia frente a REST.

📦 ¿Qué es gRPC y por qué revoluciona los Microservicios?

Creado por Google en 2015 y adoptado por la CNCF, gRPC (Google Remote Procedure Call) sustituye el modelo tradicional de endpoints REST basados en cadenas de texto JSON por invocación directa de métodos tipados mediante contratos estrictos definidos en archivos .proto:

TRANSPORTE HTTP/2

Multiplexación Real

Múltiples llamadas RPC concurrentes viajan bidireccionalmente sobre una única conexión TCP persistente, eliminando el bloqueo en cabeza de línea (Head-of-Line Blocking) a nivel de aplicación.

SERIALIZACIÓN BINARIA

Protocol Buffers (Protobuf)

En lugar de enviar nombres de campos repetitivos como "nombre_cliente": "Ana" en texto ASCII, Protobuf usa tags numéricos enteros (1, 2, 3...) y codificación de longitud variable (Varints), logrando cargas útiles 70% a 85% más compactas.

CONTRATOS FUERTES

Generación de Código Agnóstica

Un único archivo contrato.proto genera automáticamente clientes y servidores fuertemente tipados en C#, Go, Java, Python, Rust o C++ sin discrepancias manuales de documentación.

📜 Definición de Servicio en Protocol Buffers (.proto): 

syntax = "proto3";
option csharp_namespace = "MaterialVisual.GrpcServices";

// Definición del Servicio
service FacturacionService {
  // 1. Unary: 1 petición -> 1 respuesta
  rpc GenerarFactura (FacturaRequest) returns (FacturaReply);

  // 2. Server Streaming: 1 petición -> Flujo de eventos
  rpc TransmitirCotizaciones (CotizacionRequest) returns (stream CotizacionReply);

  // 3. Client Streaming: Flujo de paquetes -> 1 resumen
  rpc SubirTelemetria (stream TelemetriaData) returns (ResumenUpload);

  // 4. Bidirectional: Flujo full-duplex simultáneo
  rpc ChatOperativo (stream MensajeChat) returns (stream MensajeChat);
}

// Mensajes fuertemente tipados con tags numéricos
message FacturaRequest {
  int32 pedido_id = 1;     // El tag = 1 es el identificador binario
  string rfc_cliente = 2;  // Tag = 2
  double monto_total = 3;  // Tag = 3
}

PATRÓN 1

1. Unary RPC

Petición simple $\rightarrow$ Respuesta simple (1 a 1).

PATRÓN 2

2. Server Streaming

1 petición $\rightarrow$ Flujo continuo de respuestas del servidor.

PATRÓN 3

3. Client Streaming

Flujo de envíos del cliente $\rightarrow$ 1 sola respuesta resumen.

PATRÓN 4

4. Bidirectional

Full-Duplex: Cliente y servidor transmiten simultáneamente.

⚖️ Duelo de Carga Útil: Protobuf vs JSON

Compara exactamente el mismo objeto de negocio (un pedido con 5 propiedades) serializado en formato JSON legible por humanos frente a Protocol Buffers binario comprimido con Varints:

JSON (Texto Plano UTF-8) 152 Bytes 
{
  "id": 10452,
  "cliente": "Carlos Morales",
  "total": 8450.50,
  "pagado": true,
  "moneda": "MXN"
}
Desperdicio: Se repiten los nombres de las claves en texto "cliente", "total", comillas y llaves en cada paquete enviado.
Protobuf (Binario Compacto) 31 Bytes (-80% Reducción)
08 D4 51 12 0E 43 61 72 6C 6F 73 20 4D 6F 72 61 6C 65 73 19 00 00 00 00 80 84 C0 40 20 01 2A 03 4D 58 4E
Optimización: Cada campo se almacena como (tag << 3) | wire_type seguido del valor en Varint binario sin metadatos de texto superfluos.
Tasa de Reducción de Bytes: 79.6%
Tráfico en 10,000,000 requests: 310 MB (vs 1.52 GB en JSON)
Ahorro de Ancho de Banda: ~1.21 GB Menos en Red

⚡ Análisis de Multiplexación HTTP/2 vs Conexiones REST HTTP/1.1

En HTTP/1.1 tradicional (REST), los navegadores y microservicios deben abrir múltiples conexiones TCP paralelas (típicamente hasta 6) sufriendo latencia por el handshake TCP/TLS. En gRPC sobre HTTP/2, todos los requests viajan en paralelo mediante multiplexación de flujos (Streams).

Dimensión Arquitectónica REST Tradicional (HTTP/1.1 + JSON) gRPC Moderno (HTTP/2 + Protobuf)
Protocolo de Transporte HTTP/1.1 (o HTTP/2 en navegadores modernos) HTTP/2 nativo obligatorio
Formato de Carga Útil Texto plano JSON (Human-readable, pesado) Binario empaquetado Protobuf (Máxima velocidad)
Contrato de Interfaz Opcional (OpenAPI / Swagger desacoplado) Estricto y obligatorio (archivo .proto)
Streaming Limitado (Server-Sent Events unidireccional, WebSockets separado) Nativo en 4 modalidades (incluyendo bidireccional)
Compresión de Cabeceras No (las cabeceras viajan repetidas en texto en cada request) HPACK (comprime y deduplica cabeceras en memoria)
Caso de Uso Idóneo APIs públicas para navegadores y terceros móviles Comunicación interna inter-microservicios de alta frecuencia
