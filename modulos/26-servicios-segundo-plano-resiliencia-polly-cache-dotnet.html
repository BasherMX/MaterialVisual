Servicios de Fondo, Resiliencia & Caché

Infraestructura y resiliencia en .NET 8+: tareas en segundo plano con BackgroundService y IHostedService, apagado elegante (*graceful shutdown*) con CancellationToken, estrategias de caché local vs distribuida (IMemoryCache vs Redis) con políticas de expiración, y tolerancia a fallos con Circuit Breaker (Polly).

⚙️ Servicios en Segundo Plano: La Jerarquía de Hosting en .NET

En ASP.NET Core y Worker Services, ejecutar tareas continuas de larga duración exige integración con el ciclo de vida del contenedor de hospedaje (IHost). No todas las opciones son componentes de infraestructura:

INTERFAZ BASE

IHostedService

Contrato primitivo que define dos métodos: StartAsync(CancellationToken) y StopAsync(CancellationToken).

Rol: Ideal para inicializaciones rápidas previas al arranque del servidor web (ej. migraciones de BD o calentamiento de caché).
CLASE ABSTRACTA RECOMENDADA

BackgroundService

Implementa IHostedService y expone el método plantilla: protected abstract Task ExecuteAsync(CancellationToken stoppingToken).

Rol: Diseñado específicamente para bucles de procesamiento continuo (colas RabbitMQ, telemetría o cron jobs internos).
ANTIPATRÓN EN INFRAESTRUCTURA

TaskFactory / Task.Run

Clases auxiliares para despachar tareas al ThreadPool. NO son servicios hospedados.

Peligro: No escuchan la señal de parada del Host; si el servidor se apaga, las tareas se matan abruptamente perdiendo datos en vuelo.

📜 Patrón Canónico: Consumo de Scopes con IServiceScopeFactory

Un BackgroundService se registra como Singleton en el contenedor IoC. Si intentas inyectar directamente un DbContext (que es Scoped), provocarás una excepción de Captive Dependency. La solución profesional es inyectar IServiceScopeFactory: 

public class ProcesadorPagosWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ProcesadorPagosWorker> _logger;

    public ProcesadorPagosWorker(IServiceScopeFactory scopeFactory, ILogger<ProcesadorPagosWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Creamos un scope efímero por cada ciclo para liberar memoria y contextos de BD
            using (var scope = _scopeFactory.CreateScope())
            {
                var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await dbContext.ProcesarPagosPendientesAsync(stoppingToken);
            }

            // Espera asíncrona sensible al token de cancelación
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}

🛑 Cancelación Cooperativa & Apagado Elegante (Graceful Shutdown)

En .NET la cancelación es estrictamente cooperativa. El runtime no aborta los hilos a la fuerza (el obsoleto Thread.Abort lanza excepciones fatales de corrupción de memoria). En su lugar, el Host emite una señal a través del CancellationToken y otorga una ventana de cortesía (por defecto 5 segundos) para terminar las transacciones en vuelo:

🗄️ Estrategias de Caché: En Memoria vs Distribuida

Al diseñar arquitecturas de alto rendimiento en .NET, la elección entre IMemoryCache y IDistributedCache (Redis) impacta directamente la escalabilidad horizontal y la consistencia de datos:

Criterio Arquitectónico IMemoryCache (Local en RAM) IDistributedCache (Redis / Clúster)
Ubicación Física Memoria RAM interna del proceso de la aplicación. Servidor externo dedicado o clúster de Redis / SQL Server.
Velocidad / Latencia Sub-microsegundos (acceso directo a punteros en Heap). 1 a 5 milisegundos (viaje de red TCP + serialización).
Escalabilidad Horizontal Aislada: Cada réplica en Kubernetes tiene su propia caché desincronizada. Compartida: Todas las réplicas leen y escriben sobre la misma fuente de verdad.
Supervivencia a Reinicios Se pierde por completo al reiniciar el contenedor web. Persistente: Los datos sobreviven a reinicios y despliegues de la app.
Serialización No requerida (almacena objetos .NET nativos). Obligatoria (requiere convertir a byte[] o JSON).

⏱️ Expiración Absoluta vs Expiración Deslizante (Sliding)

- Absoluta: El dato expira puntualmente tras $N$ segundos desde su inserción, sin importar cuántas veces se consulte.
- Deslizante (Sliding): El tiempo de vida se renueva cada vez que alguien lee el dato.
- La Regla de Oro: ¡Combina ambas! Si solo usas Sliding, un dato consultado constantemente por un bot nunca expirará, manteniendo datos obsoletos eternamente en memoria.

options.SetSlidingExpiration(TimeSpan.FromSeconds(5));
options.SetAbsoluteExpiration(TimeSpan.FromSeconds(15)); // Techo máximo obligatorio
TIEMPO DE VIDA RESTANTE: 10.0s (Caché Válida)

⚡ Resiliencia Web: El Patrón Circuit Breaker (Polly)

Cuando un servicio remoto aguas abajo (*downstream*) colapsa, seguir bombardeándolo con peticiones empeora la catástrofe y satura los hilos de tu propio servidor. El patrón Circuit Breaker actúa como un fusible eléctrico de protección:

CORRIENTE NOMINAL: 100% (FLUJO ACTIVO)
SENSOR DE FALLAS: 0 / 3 CONSECUTIVAS
DISYUNTOR: CERRADO
ESTADO 1

CERRADO (Closed)

Operación normal. El disyuntor hace contacto firme y los pulsos viajan al foco encendiéndolo a máxima potencia.

ESTADO 2

ABIERTO (Open)

Disyuntor levantado tras 3 fallos. Corta la corriente: el foco se apaga y los pulsos rebotan en seco (fail-fast).

ESTADO 3

SEMI-ABIERTO (Half-Open)

Período de prueba prolongado. El foco se enciende levemente al 25% con corriente de sonda mientras espera peticiones.

TELEMETRÍA DE LLAMADAS A API EXTERNA: Fallos: 0 / 3 consecutivos | Estado: CERRADO
[CIRCUITO CERRADO]: Sistema saludable. Disyuntor conectado, conduciendo corriente y foco encendido plenamente.

📚 Librerías Esenciales del Ecosistema .NET 8 (Mark J. Price)

En su obra canónica Apps and Services with .NET 8, Mark J. Price destaca tres librerías de infraestructura estándar de la industria que resuelven problemas críticos de multiplataforma, observabilidad y resiliencia en servidores de producción:

GRÁFICOS MULTIPLATAFORMA

Six Labors ImageSharp

Librería estándar moderna 100% código administrado C# para procesamiento y manipulación de imágenes 2D en servidores y microservicios.

  • El Problema Resuelto: System.Drawing.Common dependía internamente de GDI+ nativo de Windows. Desde .NET 6+, Microsoft la marcó como obsoleta y lanza PlatformNotSupportedException en Linux/macOS.
  • Capacidades: Redimensionar, recortar, marcas de agua, filtros, compresión JPEG/PNG/WebP sin fugas de memoria nativa.
  • Totalmente Asíncrona: Métodos nativos SaveAsJpegAsync y LoadAsync para no bloquear hilos en ASP.NET Core.
LOGGING ESTRUCTURADO

Serilog

Librería de facto para Logging Estructurado (*Structured Logging*) mediante plantillas de mensajes enriquecidas (*Message Templates*).

  • El Salto Cualitativo: Los logs de texto plano concatenado son imposibles de filtrar o indexar. Serilog preserva los valores como pares clave-valor fuertemente tipados.
  • Sintaxis: Log.Information("Pedido {OrderId} procesado para {UserId}", id, user);.
  • Sinks Desacoplados: Exporta a Seq, Elasticsearch, Azure Application Insights, AWS CloudWatch o archivos JSON rotativos sin tocar la lógica de negocio.
RESILIENCIA & TOLERANCIA A FALLOS

Polly

Framework de resiliencia y manejo de fallos transitorios que permite definir políticas declarativas y fluidas para llamadas HTTP, SQL y RPC.

  • Políticas Reactivas: Retry (Reintentos con retroceso exponencial y Jitter aleatorio) y Circuit Breaker (protección de sobrecarga).
  • Políticas Proactivas: Timeout, Rate Limiter y Hedging (disparar peticiones redundantes paralelas).
  • Integración en .NET 8: Adoptada oficialmente por Microsoft mediante Microsoft.Extensions.Resilience (paquete Microsoft.Extensions.Http.Resilience).
