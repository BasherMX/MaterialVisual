JWT: Tokens & Criptografía

Mecanismo estándar de autenticación y autorización sin estado (Stateless RFC 7519). Descubre la anatomía de Header, Payload y Signature, la diferencia crítica entre firmar y cifrar y la rotación segura de Refresh Tokens.

🔐 La Estructura Tripartita de un JSON Web Token

Un JWT se compone de tres cadenas codificadas en Base64Url separadas por puntos (.). Cada segmento cumple una función criptográfica precisa:

PARTE 1 · ROJO

Header (Encabezado)

Indica el tipo de token y el algoritmo de firma criptográfica utilizado. 

{
  "alg": "HS256",
  "typ": "JWT"
}
PARTE 2 · PÚRPURA

Payload (Claims / Afirmaciones)

Contiene las afirmaciones sobre la identidad y permisos del usuario. 

{
  "sub": "10452",
  "name": "Carlos Morales",
  "role": "Usuario",
  "exp": 1793473000
}
PARTE 3 · CIAN

Signature (Firma Digital)

Garantiza que el contenido no fue alterado en tránsito. Se calcula con: 

HMACSHA256(
  base64Url(Header) + "." +
  base64Url(Payload),
  secret_key
)

⚠️ Regla de Oro de Seguridad: UN JWT FIRMADO NO ESTÁ ENCRIPTADO

Cualquier intermediario (el navegador, un proxy o un atacante) puede tomar la cadena del Payload y ejecutar atob() en JavaScript para leer los datos en texto plano. La firma solo verifica integridad (que nadie haya alterado los datos sin conocer la clave secreta). Por tanto, NUNCA almacenes contraseñas, claves privadas ni datos de tarjetas de crédito dentro de un JWT.

Modifica los Claims en el editor de la izquierda o altera la clave secreta. Observa cómo cambia la cadena JWT resultante o pulsa "Simular Ataque de Manipulación" para ver cómo el servidor rechaza la firma si un atacante intenta elevar sus privilegios sin la clave.

🚨 ¡DETECCIÓN DE MANIPULACIÓN: Invalid Signature!

El atacante cambió el claim "role": "Usuario" a "role": "SuperAdmin" en el Payload. Al recalcular la firma con la clave secreta del servidor, el hash no coincide. El servidor rechaza inmediatamente la petición con HTTP 401 Unauthorized.

Nota: En producción, algoritmos asimétricos (ej. RS256) firman con Clave Privada y validan con Clave Pública, permitiendo a múltiples microservicios validar tokens sin compartir el secreto.

🔄 Estrategia de Ciclo de Vida: Access Token vs Refresh Token

Un JWT sin estado (Stateless) no puede revocarse fácilmente antes de su expiración. Por eso, la industria utiliza un esquema de dos tokens: un Access Token de vida corta y un Refresh Token de larga duración almacenado de forma segura:

ACCESS TOKEN (Vida útil: 15 minutos simulados): Tiempo restante: 100%
📋 TRAZA DE RED DE AUTENTICACIÓN (OAuth 2.0 / OIDC):
[AUTH]: Access Token emitido con claim 'exp' = +15min. Usuario autenticado.

🛡️ Vulnerabilidades Críticas y Almacenamiento Seguro

El mayor dilema arquitectónico de JWT es dónde almacenarlo en el navegador para defenderse simultáneamente de ataques XSS y CSRF:

Mecanismo de Almacenamiento Vulnerabilidad a XSS Vulnerabilidad a CSRF Veredicto y Recomendación
LocalStorage / SessionStorage ALTA: Cualquier script inyectado (XSS) puede leer localStorage.getItem('token') y robarlo. NULA: El token no se envía automáticamente en peticiones de formulario. Desaconsejado para datos críticos; vulnerable al robo total de sesión por dependencias npm maliciosas.
Cookie con HttpOnly + Secure + SameSite=Strict NULA: JavaScript no tiene acceso a la cookie (inmune a lectura por XSS). MITIGADA: El navegador envía la cookie solo al mismo origen gracias a SameSite=Strict. ESTÁNDAR RECOMENDADO: Almacenar el Refresh Token en cookie HttpOnly y el Access Token en memoria volátil de la app.
