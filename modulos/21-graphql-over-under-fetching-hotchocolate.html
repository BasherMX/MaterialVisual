GraphQL & HotChocolate

El paradigma de consulta declarativa que erradica el Over-fetching y Under-fetching de las APIs REST. Explora Queries, Mutations y la integración con Entity Framework Core mediante HotChocolate en .NET.

⚖️ Las Dos Grandes Patologías de las APIs REST Rígidas

En la arquitectura REST clásica, los endpoints devuelven una estructura de datos fija decidida por el desarrollador de backend. Esto genera dos problemas estructurales en aplicaciones web y móviles modernas:

PATOLOGÍA 1

Over-fetching (Sobredescarga)

El servidor entrega **muchos más datos de los necesarios**.

Ejemplo: La app móvil solo necesita mostrar el nombre del usuario en la barra superior, pero el endpoint GET /api/usuarios/1 descarga 45 campos: dirección, CURP, historial de compras, geolocalización y preferencias (8 KB descargados para usar 12 bytes).
PATOLOGÍA 2

Under-fetching (Subdescarga & N+1)

Un endpoint **no entrega suficiente información**, obligando a emitir múltiples peticiones en cascada.

Ejemplo: Para pintar la pantalla de una factura, el cliente debe hacer 3 llamadas secuenciales: GET /pedidos/10 ➔ GET /clientes/5 ➔ GET /pagos/3. Cada petición añade 150ms de latencia de red en conexiones móviles 4G/5G.
LA SOLUCIÓN

GraphQL: Contrato Declarativo

El cliente solicita **exactamente la forma y las propiedades que necesita en un solo viaje de red**.

Resultado: Cero datos sobrantes (0% Over-fetching) y cero peticiones en cascada (0% Under-fetching): 1 Request ➔ 1 Response con la forma exacta.

☕ HotChocolate en .NET: La Fusión de GraphQL con Entity Framework Core

          

            HotChocolate es el servidor de GraphQL de alto rendimiento para ASP.NET Core. Su ventaja crítica es el soporte de middlewares sobre IQueryable<T>, traduciendo las peticiones GraphQL directamente a sentencias SQL optimizadas en el motor de base de datos:
          


          

            
            

              

                1. Query Type en C# (HotChocolate)
              

              
public class Query
{
    // Las proyecciones inspeccionan la consulta GraphQL
    [UseProjection] // Solo proyecta columnas solicitadas
    [UseFiltering]  // Habilita WHERE dinámico en GraphQL
    [UseSorting]    // Habilita ORDER BY dinámico
    public IQueryable<Pedido> GetPedidos([Service] AppDbContext db)
    {
        return db.Pedidos; // Retorna IQueryable puro
    }
}

            


            
            

              

                2. Sentencia SQL Generada en la BD
              

              
-- ¡Cero columnas innecesarias en el SELECT!
-- HotChocolate + EF Core proyectan solo lo pedido:
SELECT 
    p.Id, 
    p.Total, 
    c.Nombre
FROM Pedidos AS p
INNER JOIN Clientes AS c ON p.ClienteId = c.Id
ORDER BY p.Total DESC

            

          


          
          

            

              
                

                  Atributo HotChocolate
                  Equivalente LINQ / SQL
                  Beneficio Arquitectónico
                

              
              
                

                  [UseProjection]
                  .Select(p => new { ... })
                  Evita traer todas las columnas de la tabla; SQL solo lee del disco las columnas exactas solicitadas.
                

                

                  [UseFiltering]
                  .Where(...)
                  Permite al frontend filtrar por cualquier propiedad sin escribir endpoints REST dedicados (ej. where: { total: { gt: 1000 } }).
                

                

                  [UseSorting]
                  .OrderBy(...)
                  Ordenamiento dinámico ascendente o descendente en tiempo de compilación SQL.
                

              
            

          

        

      


      
      

        

          
⚡ Queries vs Mutations: Anatomía y Equivalencias REST

          

            En GraphQL no existen verbos HTTP como GET, POST, PUT o DELETE. Toda operación se envía por HTTP POST al endpoint único /graphql clasificándose en dos operaciones principales:
          


          

            

              

                🔍 QUERY (Operación de Lectura · Equivalente a GET)
              

              
query ObtenerFactura($id: ID!) {
  pedido(id: $id) {
    id
    fecha
    total
    cliente {
      nombre
      rfc
    }
  }
}

              

                Idempotente y sin efectos secundarios. Puede ser paralelizado de forma segura por el motor.
              

            


            

              

                ✏️ MUTATION (Operación con Efectos Secundarios · POST/PUT/DELETE)
              

              
mutation RegistrarPago($input: PagoInput!) {
  aplicarPago(input: $input) {
    pagoId
    estado
    saldoRestante
  }
}

              

                Ejecución estrictamente secuencial para garantizar consistencia transaccional del negocio.
